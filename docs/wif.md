# workload identity federation for the tailscale api

tailgate talks to the tailscale api in two places:

- **e2e** (`test/e2e/*.go`, build tag `e2e`) creates and tears down a throwaway ephemeral
  tailnet per run via an **org-level** token — `internal/tailnet` POSTs to
  `/api/v2/organizations/-/tailnets`, then uses the per-tailnet child oauth client the
  response hands back for acl/keys/delete. **In CI this org token comes from workload
  identity federation — no long-lived secret** (locally it falls back to
  `TS_ORG_OAUTH_CLIENT_ID` / `TS_ORG_OAUTH_CLIENT_SECRET`).
- **the operator** (`cmd/tailgate-operator`) still uses a **tailnet-scoped** oauth client
  (`TS_OAUTH_CLIENT_ID` / `TS_OAUTH_CLIENT_SECRET`, from the `tailgate-tailnet-creds`
  secret) to mint gateway authkeys and delete gateway devices on teardown
  (`internal/tsclient`). Moving this to wif is future work.

workload identity federation (wif): the github actions job proves who it is with a
github-signed oidc token, exchanges it at tailscale for a short-lived api access token, and
uses that token instead of an oauth client secret. nothing long-lived is stored in github
secrets.

**implemented for the e2e** (`.github/workflows/test-e2e.yml`): the job declares
`id-token: write`, fetches a github oidc jwt for the audience `api.tailscale.com/<client-id>`,
exchanges it at `/api/v2/oauth/token-exchange` for an org access token, and passes it to the
harness as `TS_API_ACCESS_TOKEN` (`internal/tailnet.NewFromAccessToken`). this is the same
flow tailvoy uses (`integration_test/scripts/exchange-oidc-token.sh` +
`.github/workflows/integration-test.yml`).

## the token-exchange flow

```
github actions job                 github oidc provider           tailscale api
------------------                 --------------------           -------------
1. request id-token  ───────────►  mint JWT
   (aud = api.tailscale.com/<client_id>)
   ◄─────────────────────────────  signed JWT

2. POST /api/v2/oauth/token-exchange ───────────────────────────► verify JWT against
   client_id=<client_id>                                           the federated
   jwt=<signed JWT>                                                 credential
   (form-encoded)                                                  (issuer/subject/aud)
                                    ◄─────────────────────────────  { "access_token": ... }
                                                                    short-lived

3. use access_token as a bearer token against /api/v2/* ────────► org / tailnet ops
```

three things have to line up for step 2 to succeed:

1. the **issuer** of the JWT (`https://token.actions.githubusercontent.com`) is trusted
   by the federated credential.
2. the **subject** (`sub`) claim of the JWT matches the subject configured on the
   credential — this is how you scope it to *your* repo/branch and not every repo on
   github.
3. the **audience** (`aud`) claim of the JWT equals `api.tailscale.com/<client_id>` —
   the github runner sets this by passing `&audience=...` when it requests the id-token,
   and the credential validates it.

### the endpoint

```
POST https://api.tailscale.com/api/v2/oauth/token-exchange
Content-Type: application/x-www-form-urlencoded

client_id=<federated identity client id>
jwt=<github-signed oidc JWT>
```

on success tailscale returns a json body with `access_token` (a short-lived oauth
bearer token). **use it immediately and never persist it** — when it expires, repeat the
exchange to get a fresh one. this is the same shape as the ordinary
`/api/v2/oauth/token` client-credentials response, just sourced from a JWT instead of a
client secret.

## configuring the tailnet (one-time, admin console)

a tailnet admin establishes the trust once, under **settings → trust credentials** in the
admin console (the same place oauth clients live). create a new credential of type
**openid connect** for github actions:

| field | value |
| --- | --- |
| **issuer** | `https://token.actions.githubusercontent.com` (github's oidc provider) |
| **subject** | the github `sub` you want to allow, e.g. `repo:rajsinghtech/tailgate:ref:refs/heads/main` to allow only `main`, or `repo:rajsinghtech/tailgate:*` to allow any ref/PR in the repo. tokens whose `sub` doesn't match are rejected. |
| **audience** | generated by tailscale as `api.tailscale.com/<client id>` — the github job must request its id-token with this exact `aud`. |
| **tag** | the federated identity isn't a user, so it acts as a tagged identity. use e.g. `tag:ci`. |
| **scopes** | the api capabilities the minted token carries. e2e needs at least `auth_keys` (mint gateway authkeys) and the device read/delete capability for teardown. give it only what the job needs. |

the credential's **client id** is what you feed to `hack/wif-exchange.sh` and what forms
the audience. there is no client *secret* — that's the entire point. the client id is not
sensitive (it appears in workflow logs and the audience), so it can live in the workflow
file or as a plain (non-secret) repo variable.

> github `sub` format reference: `repo:<owner>/<repo>:ref:refs/heads/<branch>` for a
> branch push, `repo:<owner>/<repo>:pull_request` for PR events, `repo:<owner>/<repo>:*`
> for any. PRs from forks do **not** get `id-token: write`, so wif-backed jobs only run
> for branches in this repo, which is the correct security boundary for ci that mints
> real tailnet credentials.

### org-level vs tailnet-scoped credentials

tailgate's e2e needs the **org** capability (create/delete tailnets), which the operator
does not. you can model this two ways:

- **one org-scoped federated credential** that the e2e exchange uses directly for the
  `/api/v2/organizations/-/tailnets` calls. the operator under test still uses the
  per-tailnet child oauth client that the create response returns (unchanged — that child
  client is born inside the ephemeral tailnet and is thrown away with it).
- **separate credentials** if you also want a wif-backed operator in a *persistent*
  tailnet (see below): a second credential scoped to that tailnet with just `auth_keys` +
  device-delete, distinct from the org credential.

the simplest migration keeps the operator's per-run creds exactly as they are (child of
the ephemeral tailnet) and only swaps the **org secret** for a wif exchange. that removes
the one long-lived secret the repo actually stores.

## how the e2e ci uses it

> **live**: this is implemented in `.github/workflows/test-e2e.yml`. The shipped job does the
> exchange **inline** (no helper script) and passes the token to the harness as
> `TS_API_ACCESS_TOKEN`, which `internal/tailnet.NewFromAccessToken` consumes. The
> helper-script variant below is an equivalent reference.

the job needs `id-token: write` so github will mint oidc tokens for it. the exchange step
runs `hack/wif-exchange.sh`, masks the result, and passes it to the tailnet-setup steps
in place of an org oauth secret.

```yaml
permissions:
  id-token: write   # lets the job request a github oidc JWT
  contents: read

env:
  # not a secret: the federated identity client id (also forms the audience).
  TS_FED_CLIENT_ID: TbqNGJkY5611CNTRL-kz4CwX2LK721CNTRL   # example — use your credential's id

jobs:
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6

      # exchange the github oidc token for a short-lived tailscale org access token.
      # hack/wif-exchange.sh mints the JWT (aud = api.tailscale.com/$TS_FED_CLIENT_ID)
      # from the ACTIONS_ID_TOKEN_REQUEST_* env vars github injects, then POSTs it to
      # /api/v2/oauth/token-exchange and prints the access token.
      - name: exchange oidc token for tailscale api token
        id: ts
        run: |
          ACCESS_TOKEN=$(hack/wif-exchange.sh "$TS_FED_CLIENT_ID")
          echo "::add-mask::$ACCESS_TOKEN"
          echo "access_token=$ACCESS_TOKEN" >> "$GITHUB_OUTPUT"

      - uses: actions/setup-go@v6
        with:
          go-version-file: go.mod
          cache: true

      # the e2e harness reads the org access token directly (no client secret).
      - name: run e2e
        env:
          TS_API_ACCESS_TOKEN: ${{ steps.ts.outputs.access_token }}
        run: make e2e
```

if you'd rather keep the exchange inline (no helper script), the two steps are exactly
what tailvoy does:

```yaml
      - name: get github oidc token
        id: oidc
        run: |
          JWT=$(curl -sS -H "Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
            "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=api.tailscale.com/$TS_FED_CLIENT_ID" \
            | jq -r '.value')
          echo "::add-mask::$JWT"
          echo "jwt=$JWT" >> "$GITHUB_OUTPUT"

      - name: exchange for access token
        id: ts
        run: |
          ACCESS_TOKEN=$(curl -s -X POST https://api.tailscale.com/api/v2/oauth/token-exchange \
            -H "Content-Type: application/x-www-form-urlencoded" \
            -d "client_id=$TS_FED_CLIENT_ID" \
            -d "jwt=${{ steps.oidc.outputs.jwt }}" | jq -r '.access_token')
          echo "::add-mask::$ACCESS_TOKEN"
          echo "access_token=$ACCESS_TOKEN" >> "$GITHUB_OUTPUT"
```

### code change in the e2e harness (implemented)

`internal/tailnet.New(orgID, orgSecret)` mints an org access token via
`/api/v2/oauth/token`. With wif the job already holds an org access token, so the harness
accepts a **pre-minted token** instead:

- `tailnet.NewFromAccessToken(token)` skips the `oauthToken()` client-credentials step and
  uses the bearer token directly for the org create/list calls (`orgToken()` returns it).
- the existing `New(id, secret)` path stays for local runs from `code/.env`. The shared
  `newTailnetClient(t)` helper picks whichever env is present: `TS_API_ACCESS_TOKEN`
  (ci/wif) over `TS_ORG_OAUTH_CLIENT_ID/SECRET` (local).

the per-tailnet child oauth client that `Create` returns is unchanged — it's minted inside
the ephemeral tailnet and used for acl/keys/delete and as the operator-under-test's creds,
exactly as now.

## using wif for the operator (persistent tailnets)

the operator can use wif too, but only where it can reach an oidc provider — i.e. when it
runs on infrastructure that issues workload identity tokens (gke/eks/aks with a projected
sa token, github actions, etc.). in a vanilla self-hosted cluster with no cloud oidc, the
operator still needs an oauth client or authkey.

where wif is available, the pattern is:

1. create a federated credential scoped to the operator's tailnet with `auth_keys` +
   device-delete scopes and a tag like `tag:tailgate`.
2. give the operator the platform oidc token (e.g. mount a projected serviceaccount token
   with `audience: api.tailscale.com/<client_id>`).
3. the operator exchanges it at `/api/v2/oauth/token-exchange` for a short-lived api token
   and refreshes on expiry, replacing the `tsapi.OAuth{ClientID, ClientSecret}` auth in
   `internal/tsclient` with a token source that does the exchange. the official
   `tailscale.com/client/tailscale/v2` client takes any `http.RoundTripper`-style auth, so
   this is a token-source swap, not a rewrite.

this removes `TS_OAUTH_CLIENT_SECRET` from `tailgate-tailnet-creds`; you keep only the
non-secret federated client id and the tailnet name. for the common self-hosted case where
no oidc issuer is available, the static oauth client remains supported and unchanged.

## quick local test of the exchange

you can't mint a real github oidc token outside actions, but you can validate the exchange
half against any JWT your credential trusts:

```bash
# inside a github actions job (id-token: write set), this works end to end:
hack/wif-exchange.sh "$TS_FED_CLIENT_ID"

# locally, pass a JWT you already hold (e.g. captured from a prior run, for debugging):
hack/wif-exchange.sh "$TS_FED_CLIENT_ID" "$SOME_JWT"
```

the script prints only the access token on stdout (everything else is stderr), so
`TOKEN=$(hack/wif-exchange.sh "$TS_FED_CLIENT_ID")` captures it cleanly.

## why this is better than a static secret

- nothing long-lived in github secrets — no oauth client secret to rotate, leak, or
  exfiltrate from a compromised workflow.
- the minted token is short-lived and scoped to exactly the capabilities the credential
  grants (`auth_keys` etc.), not a full oauth client.
- trust is pinned to the repo (and optionally branch) via the `sub` claim, so a fork or a
  different repo can't mint tailgate tokens even if it knows the (non-secret) client id.
